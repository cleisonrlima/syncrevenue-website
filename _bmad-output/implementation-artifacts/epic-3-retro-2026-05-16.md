## 3. What Went Well

1. **Review follow-through materially improved.** Epic 3 closed most carry-forward items from Epic 2: patterns gallery (A3), `defaultValue` lint (A4), token contrast manifest (A5), sandbox convention (A6), section utility consolidation (A9), and ErrorBoundary i18n/recovery (A10).
2. **The canonical Epic 2 form stack scaled cleanly.** Story 3.5 reused DAO factories, Zod validation, per-route rate limiter, API envelope strictness, fire-and-forget SMTP, hidden locale capture, in-place success states, and mobile submit-button rules for `POST /api/audit`.
3. **Testing became more enforceable.** The epic added or strengthened Playwright coverage for mobile UX, SEO, commission audit, and responsive overlays; added a lint gate to CI; and made contrast validation reproducible through a generated manifest.
4. **Frontend primitives matured.** `SectionHeader`, `SectionSkeleton`, `GradientButton`, `MotionSection`, `ErrorBoundary`, and `ScrollRestoration` are now more reusable and better documented.
5. **Documentation stopped being passive.** The patterns gallery, sandbox convention, architecture-token docs, and retro updates turned learned behavior into references that future stories can cite.
6. **SEO shipped as a coherent system.** Runtime head management, querystring locale detection, hreflang alternates, sitemap/robots generation, OG metadata, and EN canonical alignment are now covered by unit and browser tests.

## 4. What Could Be Better

1. **Story 3.1 / 3.6 content truthfulness required an explicit override.** The team first treated placeholder assets as real content, then documented an accepted fake-data stub. The current behavior is honest in the story record, but the public Team section still needs real stakeholder content before production.
2. **Lighthouse mobile remains partially unresolved.** Story 3.4 made `npm run lhci:mobile` runnable, but the run still surfaced a language-switcher contrast waiver conflict and mobile LCP above the target. Story 3.7 removed the render-blocking font `@import`, but the LHCI gate was not re-run to prove the final state.
3. **TrustBar breakpoint still differs from the UX spec.** The code uses Tailwind `sm` behavior, so the 2x2 TrustBar grid starts at 640px rather than the specified 480px.
4. **Review findings sometimes landed inside the same story after initial deferral.** This worked for Story 3.4, but it made the story record complex. The system needs a clearer rule for "patch now" vs. "new follow-up story."
5. **Some production-readiness items are still deliberately deferred.** 24-month data retention deletion, placeholder client references, broken non-empty team photo fallback, and production deployment controls remain outside Epic 3.

## 6. Key Lessons

1. **Action items need story slots, not just ownership.** Epic 3 succeeded where prior retrospectives struggled because carry-forward items became explicit stories: 3.7, 3.8, 3.9, and 3.10.
2. **Accepted fake content must be labeled as fake in the story record.** Story 3.6 did this correctly after review, but the first pass blurred the line. Future content placeholders should be documented as placeholders from the start.
3. **Quality gates are more useful when they are codified.** The ESLint rule, contrast manifest, and sandbox convention removed recurring review work.
4. **SEO in an SPA needs explicit conventions.** Runtime canonical, static `index.html`, sitemap `<loc>`, hreflang, `x-default`, and `?lng=` need a documented rule so review does not rediscover the same tradeoff.
5. **Mobile quality requires both layout tests and performance proof.** Epic 3 improved layout coverage substantially, but performance/accessibility gates still need a final proof run after font and token changes.

## 7. Epic 4 Preview - Admin Operations

Epic 4 adds authenticated admin operations: login/session management, leads dashboard, lead status updates, team member CRUD, active/display ordering, and an admin navigation shell.

### Dependencies on Epic 3

- The public Team section currently uses JSON-backed fake stub data. Epic 4 stories 4.4 and 4.5 will replace that with `GET /api/team` and admin-managed records.
- The lead capture stack from Epic 2 and the audit route from Epic 3 create multiple lead surfaces. Epic 4 lead dashboard scope currently names `demo_requests`; the team should decide whether `audit_requests` and `contacts` appear in the same admin experience, separate views, or later scope.
- The i18n `defaultValue` lint rule will affect all new admin copy. New admin pages must use translated visible text with default values from the start.
- Admin tests should follow the sandbox convention and avoid claiming server-bound browser coverage when the environment blocks real-server execution.
- Existing admin auth placeholder routes from Epic 2 become real work in Story 4.1.
