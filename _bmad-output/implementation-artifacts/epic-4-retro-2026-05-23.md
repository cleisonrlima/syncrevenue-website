## 4. What Went Well

1. **Admin operations became a coherent workflow.** Login/session management, leads list/filtering, inline status updates, team CRUD, public team API, active toggle, dashboard stats, and persistent nav now form one usable admin experience.
2. **Security review findings were closed properly.** Story 4.1 identified missing login throttling and JWT revocation. Those became Stories 4.7 and 4.8, with durable counters, no-information-leak lockout responses, token versioning, stale-token rejection, and deleted-admin rejection.
3. **Route and DAO boundaries held.** Admin routes stayed behind `requireAdmin`; route handlers used DAOs rather than raw SQL; public `/api/team` was separated from auth-gated `/api/admin/team`; client helpers shape-check server responses.
4. **Test coverage scaled with risk.** The suite grew from 380 tests after Story 4.1 to a recorded 726 green tests in Story 4.6, with specific route, DAO, helper, page, layout, and E2E specs added throughout.
5. **Admin import isolation became a lived convention.** Story records repeatedly enforced that admin pages do not import from public `components/sections/*`, reducing accidental coupling between public marketing UI and internal CRM UI.
6. **Optimistic UI patterns matured.** Lead status updates and team active toggles use local optimistic updates, row-level pending state, revert-on-error behavior, and row-scoped `role="alert"` messages.
7. **Public team content moved to durable data.** The public Team section now reads active team members from the DB-backed public endpoint, selecting locale-specific role and bio fields on the client.

---

## 5. What Could Be Better

1. **The first auth story carried two security deferrals.** The deferrals were later closed, but Story 4.1 initially shipped with important hardening gaps. The system worked, but only because follow-up stories were created and completed.
2. **Some browser-level verification remained environment-dependent.** Multiple story records note E2E specs shipped while some sandbox browser projects were unavailable. This is acceptable for development, but production readiness needs recorded CI or local evidence.
3. **Full-suite reliability showed strain under security tests.** Story 4.5 recorded full-suite auth throttling timeouts under contention, followed by passing targeted and later broad runs. The later pass is good, but the risk pattern should stay visible.
4. **The admin lead scope stayed focused on `demo_requests`.** Epic 3 asked whether `contacts` and `audit_requests` should join the admin lead workflow. Epic 4 implemented the demo-request scope. That is a valid product decision, but it should be explicit.
5. **Manual UI verification gaps remain on security edge cases.** Story 4.8 left the UI-level reseed/redirect smoke unchecked because the equivalent route behavior is covered automatically. That is technically defensible, but deployment handoff should include an operator-visible check.
6. **Production content truth is still a business dependency.** Epic 4 enabled DB-backed team management, but stakeholder-approved production team content still needs ownership.

## 7. Key Lessons

1. **Security review findings need immediate story materialization.** Login throttling and token revocation were too important to remain comments; closing them as 4.7 and 4.8 strengthened the whole admin surface.
2. **Admin and public surfaces need different failure behavior.** `AdminApiError` must participate in session clearing, while public team failures must not affect admin state. Story 4.4 captured this separation through `PublicTeamError`.
3. **Optimistic UI must account for active filters.** Story 4.3 review caught stale filtered rows after mutation. Future inline mutations should test both the row update and the surrounding filtered collection state.
4. **Accessibility needs value-complete labels, not just labels.** Story 4.6 review caught a locale stats card whose accessible label omitted displayed values. Stats UI should expose the same meaning visually and programmatically.
5. **Rate-limit tests can stress full-suite execution.** Security tests that depend on timers, bcrypt, and limiter state need isolated cleanup discipline so they do not create flaky signals under parallel load.
6. **DAO boundaries make later deployment safer.** Because SQL stayed inside DAOs, Epic 5 backup, migration, and health-check work can reason about a small number of data access points.

## 8. Next Epic Preparation - Epic 5 Production Deployment

At the point of Epic 4 closure, the next planned epic is Epic 5: Production Deployment. Its core work is production build/PM2 process management, domain and SSL/TLS configuration, environment hardening, SQLite backup automation, uptime monitoring, and health checks.

### Dependencies on Epic 4

- Admin auth relies on `JWT_SECRET`, secure cookie settings, production CORS, `ALLOWED_ORIGIN`, and HTTPS.
- Admin seed behavior now creates or updates the admin user and also participates in token revocation through `token_version`.
- Admin login protection depends on the durable `admin_login_attempts` table.
- Public Team data depends on `team_members`, the idempotent team seed, and a persistent SQLite DB path outside deploy output.
- Dashboard and admin pages depend on protected `/api/admin/*` routes remaining reachable after static asset serving and reverse proxy configuration.
- The backup plan must preserve `demo_requests`, `team_members`, `admin_users`, `admin_login_attempts`, and related operational data.

### Significant Discovery Check

No Epic 4 finding invalidates Epic 5's direction. The deployment epic is still the right next step.

Epic 5 should, however, explicitly account for three facts Epic 4 introduced:

1. The admin DB now has security state (`admin_login_attempts`, `admin_users.token_version`) that must survive deploys and backups.
2. Re-running the admin seed intentionally revokes existing admin sessions, so deployment runbooks need to treat seeding as an operational action.
3. The public Team section now depends on the database, so a fresh production DB needs team seed or admin-entered team rows before launch.

**Epic update required:** No fundamental rewrite. Update the production checklist/runbook to include the items above.
